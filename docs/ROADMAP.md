# Aier 技术发展路线图

- 状态：开发规划；未标记为已实现的内容均为计划。
- 当前版本：0.1.0；里程碑完成并验证后再确定后续版本号。
- 更新日期：2026-10-04
- 学习依据：[Agent 学习与研究路线整理](AGENT_LEARNING_PATH.md)

## 1. 定位与范围

Aier 是一个从零实现的 **mini-agent framework**，以 Agent Systems / Infrastructure 为主线，逐步覆盖 Tool Use、Memory、Evaluation 与长期任务可靠性。

核心目标是让不同应用复用一套可理解、可测试的单 Agent 执行循环，再以真实任务和评测驱动扩展。当前从 OpenAI Chat Completions 格式起步；其他原生模型协议在有实际需求时增加适配器。

## 2. 当前基线

| 能力 | 实现状态 | 后续缺口 |
| --- | --- | --- |
| 模型抽象与工厂 | `LLMModel`、`get_model`、`OpenAIModel` 已有实现 | 目前只有 OpenAI 格式适配 |
| 消息与流事件 | 文本、思考、工具调用、工具结果消息和用量类型已定义 | 历史 assistant/tool 消息仍需按供应商协议转换 |
| 工具 | `Tool` 基类与 `ToolRegistry` 均存在 | 统一注册、schema 与执行路径，校验参数和错误 |
| 短期记忆 | 按消息条数维护滑动窗口 | 尚未接入 Agent；需保护完整工具调用与结果配对 |
| Agent | `BaseAgent` 定义接口 | `react_agent.py` 为空，尚无执行循环 |
| 示例与测试 | 流式对话示例、模型流回归测试、检查配置测试 | 工具示例为空，缺少 Agent 闭环与任务评测 |
| 其他能力 | 技能加载文件为空 | 长期记忆、状态持久化、恢复、MCP、多 Agent 均未实现 |

远程已有的无工具请求、usage 汇总块和流结束事件修复作为现有基线维护，不再列为待实现任务。

## 3. 设计约束

- **D1. 分层清晰**：`ai` 处理模型协议与消息转换；`agent` 处理循环、工具执行、上下文和运行状态。
- **D2. 最小可用优先**：用任务和测试推动抽象，不提前引入图编排、事件总线或复杂插件系统。
- **D3. 工具实现可复用**：先统一本地函数工具的 schema 与执行路径；MCP 是后续接入方式，不是本地工具的前置条件。
- **D4. 保留供应商参数透传**：允许通过 `**kwargs` 使用底层 SDK 参数；框架管理的 `stream` 和 `tools` 不允许调用方覆盖。
- **D5. 区分模型流和运行轨迹**：保留可用的 `thinking_*` 事件，运行轨迹另记录工具、状态和错误；支持没有推理内容的模型。
- **D6. 有限执行与明确失败**：定义终止条件、资源限制与错误结果，不把截断、异常或达到步数上限伪装成任务成功。
- **D7. 验证与数据边界**：核心测试使用模拟模型与工具；真实模型评测独立运行，凭据、私有数据和原始轨迹默认不提交。

## 4. 实现里程碑

### M0 — 收敛消息与工具契约

目标：为最小闭环准备一致的模型输入输出和工具接口。

| 任务 | 交付物 | 验证重点 |
| --- | --- | --- |
| 转换历史 assistant/tool 消息 | 供应商格式的正文、`tool_calls` 与 `tool_call_id` | 工具调用与结果配对，内部元数据不直接发送 |
| 统一 `Tool` 与 `ToolRegistry` 的使用路径 | 一套可注册、可查找、可执行的工具契约 | 重复名称、无效参数、未知工具、执行异常 |
| 完善工具调用流处理 | 按调用标识/索引组装参数 | 多调用、参数分片与无效 JSON |
| 保持模型流回归覆盖 | 现有测试与新增契约测试 | 无工具、usage 汇总块、结束原因 |

退出标准：离线测试能证明消息转换与工具调用契约正确；代码检查通过。是否删除现有抽象由实现方案决定，不预设重构方式。

### M1 — 单 Agent 最小执行闭环

目标：实现 `ReactAgent`，把现有组件接成可运行的循环。

| 任务 | 交付物 |
| --- | --- |
| 实现模型调用 → 工具执行 → 结果回填 → 继续调用 | 可复用的单 Agent 执行循环 |
| 明确成功、错误和达到步数上限的结果 | 基本运行状态与 `max_steps` |
| 接入短期上下文 | 完整保存工具调用及其观察结果 |
| 增加基本失败处理 | 参数错误和工具异常的受控反馈；不无限重试 |
| 完成工具调用示例 | `examples/model_tool_call.py` 可运行 |

退出标准：模拟模型测试覆盖无工具回答、一次工具调用、多步调用、工具失败和达到步数上限；另用实际模型验证端到端工具任务，记录环境与结果。

### M2 — 应用、运行轨迹与小型评测

目标：验证复用能力，并建立后续研究的基线。

| 任务 | 交付物 |
| --- | --- |
| 构建本地文件分析等应用示例 | 应用只配置工具与提示，不重写循环 |
| 增加另一类任务场景 | 证明同一核心循环可复用 |
| 记录运行轨迹 | 模型调用、工具参数/结果、状态、错误、耗时与可用用量 |
| 建立小型固定任务集 | 成功条件、参考结果或程序化断言 |
| 汇总评测指标 | 成功率、工具正确性、步数、token、耗时与失败类别 |

退出标准：至少两个场景复用框架；任务集可重复运行并生成报告。真实模型实验记录模型、提示、工具、预算与重复次数；不承诺模型输出完全确定。

离线轨迹回放只复现已记录行为，不重新执行工具，也不等同于重新调用模型评测。

### M3 — Memory 与 Reliability 实验

目标：选择一个明确问题，比较机制而非堆叠功能。

| 任务 | 交付物 |
| --- | --- |
| 比较完整历史、窗口与摘要策略 | 保持工具交互完整的上下文构建与对照报告 |
| 按任务需要引入长期存储或检索 | 可追溯的记忆写入与读取 |
| 注入工具超时、临时失败或错误结果 | 失败数据与恢复策略对照 |
| 比较有限重试、自纠错或重新规划 | 固定预算下的成功率与成本变化 |

退出标准：固定任务与模型等实验条件，明确基线、变量、指标及失败案例。仅在评测收益支持时将新策略作为默认行为。

### M4 — 长任务与按需扩展

目标：根据应用暴露的瓶颈完善长期任务执行。

- 运行状态与检查点：区分已完成动作、待执行动作和可恢复状态；避免恢复时重复执行有副作用的工具。
- 规划：需要时引入显式任务分解，并与原循环比较。
- MCP、技能与钩子：从具体工具接入或行为扩展需求出发。
- Coding / Computer Use：根据环境操作需要增加隔离、权限与人工介入。
- 多 Agent：单 Agent 基线稳定后才增加委托与通信，并衡量质量、耗时和成本。

退出标准：每项能力都有真实需求、独立验证和应用示例。日志本身不保证安全续跑，任务恢复需要额外的状态与副作用处理。

### M5 — Agent Learning（研究探索）

在已有可靠轨迹、任务集和反馈之后，再考虑经验抽象、策略优化或 RL。先明确学习对象、数据来源、奖励、训练资源及独立测试集，再决定实现方式。

这不是当前轻量框架发布的必要条件，也不预先承诺具体算法或版本。

## 5. 优先级与边界

- **P0：M0、M1**。先完成工具任务闭环。
- **P1：M2**。尽早建立可观察、可评测的应用基线。
- **P2：M3**。围绕 Memory 或 Reliability 聚焦实验。
- **按需推进：M4、M5**。由任务和实验结果决定。

当前不要求完整图编排、A2A、向量库、OpenTelemetry 后端或多 Agent。新增供应商与外部协议不会替代核心闭环验证；所有规划需保持小步实现和准确的能力声明。
